# Tesla T4 baseline, 2026-09-27

Historical experiment log. Statements about a "next" measurement describe
the sequence at that time. Final corrected results and the v0.1 stopping
decision are in the root README and `PROJECT_SUMMARY_CN.md`.

This is the first measured GPU baseline for the forward-only, post-projection
SwiGLU kernel. The data was produced on AutoDL instance `ecd9119ffa` with a
Tesla T4 (compute capability 7.5), Python 3.12.14, PyTorch 2.6.0+cu124,
CUDA 12.4 and Triton 3.2.0. The recorded seed is 42. The source data is in
[`t4_fp16.json`](../results/t4_fp16.json),
[`t4_fp32.json`](../results/t4_fp32.json) and
[`t4_mlp_fp16.json`](../results/t4_mlp_fp16.json). These are the original JSON
bytes from the GPU run, retained after validating the archive contents and
speedup ratios. The corresponding test run passed 17 tests and skipped five
BF16 tests because T4 does not support native BF16 Triton instructions.

## Post-projection operator

`eager` is PyTorch `F.silu(gate) * up`; `triton` is the project's fused
elementwise kernel. Both calls allocate an output. Times below are in
microseconds, converted from the original millisecond JSON values. Speedup
is eager time divided by Triton time. Each result is the median of three
`triton.testing.do_bench` medians; each `do_bench` has 50 ms warmup and 200 ms
measurement time.

| Tokens × features | FP16 eager | FP16 Triton | FP16 speedup | FP32 eager | FP32 Triton | FP32 speedup |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 × 4096 | 6.720 | 4.224 | 1.591× | 10.176 | 4.256 | 2.391× |
| 1 × 11008 | 6.720 | 4.448 | 1.511× | 7.040 | 5.280 | 1.333× |
| 128 × 4096 | 20.480 | 16.000 | 1.280× | 34.816 | 26.112 | 1.333× |
| 128 × 11008 | 55.584 | 35.360 | 1.572× | 106.496 | 63.008 | 1.690× |
| 1024 × 4096 | 153.792 | 92.160 | 1.669× | 299.584 | 177.792 | 1.685× |
| 1024 × 11008 | 397.440 | 237.920 | 1.670× | 788.480 | 468.448 | 1.683× |

Maximum absolute error against PyTorch is 0.00048828125 for FP16 and
0.0000019073486328125 for FP32. All configured tolerance checks passed.
The FP32 1 × 4096 result is a few microseconds and differs markedly from the
neighboring 1 × 11008 case; repeat it across independent runs before citing
2.391× as a stable gain.

## Synthetic LLaMA-style MLP

This measures three PyTorch linear projections and either activation path,
using random local weights and `hidden=4096`, `intermediate=11008`. Both
providers use identical projection code and weights. Times are in milliseconds.

| Tokens | FP16 eager | FP16 Triton | Speedup | Max. absolute error |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.960768 | 0.956416 | 1.00455× | 0 |
| 8 | 0.926144 | 0.922976 | 1.00343× | 0 |
| 128 | 1.511232 | 1.488960 | 1.01496× | 0 |
| 1024 | 11.644576 | 11.489536 | 1.01349× | 0.0001220703125 |

The full-layer improvement is much smaller than the standalone operator
improvement. The shared linear projections are a likely reason; the later
stage and operator traces below add evidence. In particular, sub-percent
differences for 1 and 8 tokens should not be claimed as reliable end-to-end
gains without repeated runs and variance estimates.
This experiment includes neither attention nor model generation, and uses
no model checkpoint. The two baseline paths are PyTorch eager and the
standalone Triton operator; the compiled operator comparison is below.

## Reproduce and next measurement

Run from the repository root on the GPU with this environment on `PYTHONPATH`
or an editable install:

```bash
python -m pytest -q
python benchmarks/bench_swiglu.py --dtype fp16 --output results/t4_fp16.json
python benchmarks/bench_swiglu.py --dtype fp32 --output results/t4_fp32.json
python benchmarks/bench_llama_mlp.py --dtype fp16 --output results/t4_mlp_fp16.json
```

The model-level follow-up below measures checkpoint generation with the same
inputs, precision and decoding configuration. Do not infer model throughput
from these standalone operator measurements alone.
An optional TinyLlama checkpoint harness exists in
`benchmarks/bench_hf_llama_generate.py`. Its first T4 run downloaded and
loaded the checkpoint, then halted on a strict full-model logit comparison:
315 of 4,096,000 elements exceeded `rtol=atol=0.01`, with maximum absolute
difference 0.0225830078125. This is a cumulative 22-layer output comparison,
and no generation timing was saved. The follow-up records this strict failure
separately from greedy token agreement and labels any timing exploratory if
the strict logit check still fails.

The `benchmarks/bench_mlp_stages.py` follow-up times each stage in isolation
and repeats full-layer timing, but does not report kernel launches or a
compiled baseline. Its stage times may not sum to the full-layer latency.

### Compiled PyTorch operator comparison

The original same-session measurements are in
[`t4_compiled_swiglu_fp16.json`](../results/t4_compiled_swiglu_fp16.json).
`torch.compile(swiglu_torch, backend="inductor", fullgraph=True)` is called
once before timing each shape, so compilation is excluded. All paths allocate
an output. Latencies are microseconds.

| Tokens × features | Eager | Hand-written Triton | Compiled PyTorch | Triton vs compiled |
| --- | ---: | ---: | ---: | ---: |
| 1 × 11008 | 6.848 | 4.448 | 4.448 | 1.000× |
| 128 × 11008 | 54.816 | 35.392 | 33.920 | 0.958× |
| 1024 × 11008 | 397.312 | 237.760 | 236.672 | 0.995× |

The final column is compiled latency divided by Triton latency; values below
one mean the compiled path was faster in this run. There is no observed
advantage over the compiled reference at these shapes. Repeated independent
runs would be needed to resolve the very small differences. Compared with
eager, the maximum absolute error was 0.00048828125 for the hand-written
kernel and 0.0078125 for compiled PyTorch. Both passed the comparison script's
`rtol=atol=0.01` check. The compiler may change FP16 intermediate rounding;
numerical accuracy must be considered alongside speed.

## Real TinyLlama checkpoint, FP16 generation

The saved [result](../results/t4_tinyllama_generate_fp16.json) was produced on
the same T4 using revision `fe8a4ea1ffedaf415f4da2f062534de366a451e6`
of `TinyLlama/TinyLlama-1.1B-Chat-v1.0`. The checkpoint file's SHA256 was
verified as `6e6001da2106d4757498752a021df6c2bdc332c650aae4bae6b0c004dcf14933`.
The model has 22 MLPs with hidden size 2048 and intermediate size 5632. The
script generated 16 tokens after a fixed 128-token prompt, using the same
model weights and FP16 precision for both providers. Each path was warmed up
twice; five subsequent timings alternated their order and synchronized CUDA.
The measured interval includes Python generation, attention, projections,
SwiGLU, sampling logic and cache handling.

| Path | Five timings (ms) | Median (ms) |
| --- | --- | ---: |
| Original eager MLP | 349.649, 351.085, 354.890, 351.083, 352.693 | 351.085 |
| Triton SwiGLU MLP | 401.942, 398.582, 398.945, 397.171, 392.997 | 398.582 |

Triton added 47.497 ms to the median, or 13.5% of the original latency;
original/Triton speedup was 0.881×. These are exploratory timings from one
checkpoint and one prompt, with no compiled full-model baseline. They do not
support an end-to-end acceleration claim. The standalone operator win did not
carry over to generation. Profiling is needed to attribute the extra latency.

The generated token IDs were identical. For a separate full-prompt logits
check, 315 of 4,096,000 values (0.00769%) failed `rtol=atol=0.01`;
maximum absolute error was 0.0234375 and mean absolute error was
0.0021480. There were zero top-1 mismatches among the 128 prompt positions.
The benchmark labels its result `exploratory_timing_strict_logits_failed`.
One matching generated sequence does not establish general equivalence;
the numerical deviation and behavior on other prompts require follow-up.

### Generation profiler follow-up

The [eager table](../results/t4_tinyllama_profile/eager_cuda_table.txt) and
[Triton table](../results/t4_tinyllama_profile/triton_cuda_table.txt) record one
additional generation each, in that order, under PyTorch's CPU/CUDA profiler.
The profiling tables are not wall-clock latency measurements. The subsequent
single-repeat unprofiled run also remained slower with Triton: 338.908 ms
versus 388.668 ms, consistent in direction with the five-repeat baseline.

| Profile event | Original | Triton |
| --- | ---: | ---: |
| `aten::mm` calls | 2,480 | 2,480 |
| `aten::mm` self CUDA time | 122.772 ms | 173.606 ms |
| Efficient attention calls | 352 | 352 |
| Efficient attention self CUDA time | 5.726 ms | 13.111 ms |
| `aten::silu` calls | 352 | 0 |
| `_swiglu_kernel` calls | 0 | 352 |
| Total self CPU time | 442.572 ms | 445.384 ms |
| Total self CUDA time | 159.540 ms | 249.906 ms |

The PyTorch multiply count fell from 3,264 to 2,912, exactly 352 fewer
calls, as expected when replacing one multiply per MLP invocation. The new
SwiGLU kernel took 1.378 ms total in the Triton profile. Unmodified matrix
multiplications and attention also became much slower on the GPU despite
identical call counts; their apparent changes exceed the activation time.
This one eager-then-Triton profile cannot distinguish changed GPU execution
conditions, profiling/order effects, or a real interaction from the MLP
replacement. In particular, CPU and CUDA profiler totals must not be added or
compared directly with the unprofiled generation medians. The next controlled
run repeats eager after Triton and checks GPU clocks and other activity.

The subsequent [A/B/A summary](../results/t4_tinyllama_profile_aba/summary.json)
ran eager, Triton, then eager again under the profiler. Matrix multiply self
CUDA times were 122.445, 172.554 and 164.463 ms, respectively; attention was
5.554, 13.022 and 12.300 ms. Even the unchanged original model became much
slower by the third profile. This demonstrates substantial profile-order or
GPU-state drift and invalidates attributing the profiled matrix-multiply
difference to the SwiGLU replacement. The unprofiled paired wall timings still
show a repeatable end-to-end slowdown, whose mechanism remains undetermined.
Next, measure host submission and synchronized wall time for repeated
decode-shape SwiGLU calls without profiling.

The [decode dispatch result](../results/t4_decode_dispatch_fp16.json) repeated
352 standalone 1 × 5632 FP16 calls, the TinyLlama intermediate width, with
alternating provider order and no profiler. Median CPU submission took
5.976 ms for eager and 15.640 ms for Triton, a 9.664 ms difference or about
27.5 μs per call. Synchronized total medians were 6.015 and 15.677 ms. The
result supports substantial host-dispatch overhead at decode shape, but this
synthetic sequence omits the model's linear projections, attention and cache;
it cannot account for the entire roughly 47.5 ms model-level difference by
itself. A three-way full-model control now compares the native MLP, a patched
MLP with reordered eager activation, and the patched Triton activation.

The [three-way result](../results/t4_tinyllama_mlp_variants_fp16.json) used
the same checkpoint and prompt, two warmups per path, five rotated runs, and
identical greedy token IDs. The median generation times were 333.787 ms
(native), 330.173 ms (patched but eager, reordered) and 380.521 ms (Triton).
The patched eager path did not reproduce the roughly 47–50 ms slowdown, so
the MLP monkeypatch and the gate/up evaluation order alone are not sufficient
explanations. This experiment does not yet localize Triton's added latency.
The next control instruments unsynchronized host elapsed time within each MLP
forward in a model-level run; its instrumentation changes absolute timing and
must be interpreted alongside the uninstrumented three-way result.

The [instrumented model run](../results/t4_tinyllama_mlp_host_fp16.json)
recorded 352 MLP forward calls per generation and rotated the three provider
orders across five repetitions. Its full-generation medians were 370.545 ms
(native), 371.147 ms (reordered eager) and 422.804 ms (Triton). The summed,
unsynchronized host elapsed time inside the 352 MLP calls had medians
51.568 ms, 49.445 ms and 86.515 ms, respectively. Triton therefore occupied
37.070 ms more inside MLP forwards than the reordered eager control, while
the corresponding full-generation median gap was 51.657 ms. Timing hooks
changed the absolute generation latency relative to the uninstrumented runs.
MLP host intervals may include GPU queue backpressure or synchronous calls;
they must not be subtracted from total generation time to infer a separate
GPU remainder. This evidence narrows the slowdown to the Triton activation
call path under full-model execution, without isolating Python overhead from
GPU interaction. The previously measured standalone 352-call submission gap
was only 9.664 ms; standalone activation loops do not reproduce all the
model-level interactions.

The next checkpoint-backed control adds `torch.compile(swiglu_torch,
backend="inductor", fullgraph=True)` at exactly the same post-projection call
site. The first generated sequence compiles the prefill and decode shapes;
compilation and subsequent warmups precede wall timing. The script records
greedy token agreement and strict full-prompt logit mismatches separately.
The comparison distinguishes the hand-written Triton wrapper from another
fused activation route; it does not evaluate compilation of the full MLP or
the entire model.

### Four-way compiled control and v0.1 decision, 2026-09-29

The saved [four-way result](../results/t4_tinyllama_compiled_control_fp16.json)
used the same checkpoint revision, prompt hash, FP16 setting, 128 input tokens,
16 generated tokens, two warmups per path and five order-rotated repeats.
Compilation and the first invocation were excluded from timing. Only the
SwiGLU operation after the gate/up projections was compiled; no projection,
full MLP or whole model compilation was measured.

| Path | Generation median (ms) | Versus native |
| --- | ---: | ---: |
| Native Hugging Face MLP | 352.068 | reference |
| Reordered PyTorch MLP | 350.397 | 1.671 ms faster |
| Hand-written Triton SwiGLU | 397.649 | 45.581 ms slower |
| Inductor-compiled SwiGLU | 408.143 | 56.075 ms slower |

All four paths produced identical greedy token IDs for this prompt. The
compiled path had 2,597 of 4,096,000 full-prompt logits outside
`rtol=atol=0.01` (0.0634%), maximum absolute difference 0.04296875, and
zero top-1 mismatches among 128 prompt positions. Its result is explicitly
marked exploratory because the strict logit comparison failed. The earlier
hand-written Triton strict comparison also failed, on a separate run.
Neither result establishes numerical equivalence across other prompts.

Decision: stop claiming or tuning post-projection-only SwiGLU as a T4
TinyLlama decode acceleration in v0.1. The operator benchmark remains valid
for its isolated scope, but both fused call paths lost at the checkpoint
generation level. The MLP ordering control and host-call measurements narrow
the investigation; the profiler showed GPU-state/order drift, so it cannot
assign the remaining slowdown precisely. A future v0.2 would require a
different optimization boundary, such as projection/activation integration,
plus a full-MLP compiled baseline, a prompt suite with stated numerical
criteria, and end-to-end prefill and decode benchmarks before any speed claim.
ST-Mamba research and SiLU-PTQ remain separate projects.

The first v0.2 gate is a full-MLP compiler baseline: the same TinyLlama
weights are passed as runtime tensor arguments to a compiled function that
includes the gate/up projections, SiLU and down projection. One compiled
function is used for same-shape layers. Its first invocation and two warmups
precede synchronized generation timings. Greedy token IDs and strict
full-prompt logits are checked separately; the full transformer is not
compiled. This establishes whether broadening the optimization boundary can
help before implementing another hand-written matmul kernel.

| --- | ---: | ---: |
| Native | 354.356 | reference |
| Reordered eager | 347.724 | 6.632 ms faster |
| Triton post-projection SwiGLU | 399.175 | 44.819 ms slower |

The compiled MLP accepted the existing gate, up and down weights as tensor
arguments. Compilation and first use were excluded, with two warmups per path.
All four paths produced the same greedy token IDs on this one prompt. The
compiled full MLP had 2,597 of 4,096,000 full-prompt logits outside
`rtol=atol=0.01`, maximum absolute difference 0.04296875 and zero top-1
mismatches across 128 prompt positions. Its timing is exploratory under the
project's strict accuracy criterion. PyTorch printed a warning that this GPU
has too few SMs for `max_autotune_gemm` mode; this run is neither a tuned GEMM
comparison nor evidence about other GPUs or compiler settings.
