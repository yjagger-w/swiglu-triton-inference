# Tesla T4 baseline, 2026-09-27

This is the first measured GPU baseline for the forward-only, post-projection
SwiGLU kernel. The data was produced on AutoDL instance `ecd9119ffa` with a
Tesla T4 (compute capability 7.5), Python 3.12.14, PyTorch 2.6.0+cu124,
CUDA 12.4 and Triton 3.2.0. The recorded seed is 42. The source data is in
[`t4_fp16.json`](../results/t4_fp16.json),
[`t4_fp32.json`](../results/t4_fp32.json) and
[`t4_mlp_fp16.json`](../results/t4_mlp_fp16.json). These are the original JSON
bytes from the GPU run, retained after validating the archive contents and
speedup ratios. The corresponding test run passed 17 tests and skipped five
BF16 tests because T4 does not support native BF16 Triton instructions.

## Post-projection operator

`eager` is PyTorch `F.silu(gate) * up`; `triton` is the project's fused
elementwise kernel. Both calls allocate an output. Times below are in
microseconds, converted from the original millisecond JSON values. Speedup
is eager time divided by Triton time. Each result is the median of three
`triton.testing.do_bench` medians; each `do_bench` has 50 ms warmup and 200 ms
measurement time.

| Tokens × features | FP16 eager | FP16 Triton | FP16 speedup | FP32 eager | FP32 Triton | FP32 speedup |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 × 4096 | 6.720 | 4.224 | 1.591× | 10.176 | 4.256 | 2.391× |
| 1 × 11008 | 6.720 | 4.448 | 1.511× | 7.040 | 5.280 | 1.333× |
| 128 × 4096 | 20.480 | 16.000 | 1.280× | 34.816 | 26.112 | 1.333× |
| 128 × 11008 | 55.584 | 35.360 | 1.572× | 106.496 | 63.008 | 1.690× |
| 1024 × 4096 | 153.792 | 92.160 | 1.669× | 299.584 | 177.792 | 1.685× |
| 1024 × 11008 | 397.440 | 237.920 | 1.670× | 788.480 | 468.448 | 1.683× |

Maximum absolute error against PyTorch is 0.00048828125 for FP16 and
0.0000019073486328125 for FP32. All configured tolerance checks passed.
The FP32 1 × 4096 result is a few microseconds and differs markedly from the
neighboring 1 × 11008 case; repeat it across independent runs before citing
2.391× as a stable gain.

## Synthetic LLaMA-style MLP

This measures three PyTorch linear projections and either activation path,
using random local weights and `hidden=4096`, `intermediate=11008`. Both
providers use identical projection code and weights. Times are in milliseconds.

| Tokens | FP16 eager | FP16 Triton | Speedup | Max. absolute error |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.960768 | 0.956416 | 1.00455× | 0 |
| 8 | 0.926144 | 0.922976 | 1.00343× | 0 |
| 128 | 1.511232 | 1.488960 | 1.01496× | 0 |
| 1024 | 11.644576 | 11.489536 | 1.01349× | 0.0001220703125 |

The full-layer improvement is much smaller than the standalone operator
improvement. The shared linear projections are a likely reason; the later
stage and operator traces below add evidence. In particular, sub-percent
differences for 1 and 8 tokens should not be claimed as reliable end-to-end
gains without repeated runs and variance estimates.
This experiment includes neither attention nor model generation, and uses
no model checkpoint. The two baseline paths are PyTorch eager and the
standalone Triton operator; the compiled operator comparison is below.

## Reproduce and next measurement

Run from the repository root on the GPU with this environment on `PYTHONPATH`
or an editable install:

```bash
python -m pytest -q
python benchmarks/bench_swiglu.py --dtype fp16 --output results/t4_fp16.json
python benchmarks/bench_swiglu.py --dtype fp32 --output results/t4_fp32.json
python benchmarks/bench_llama_mlp.py --dtype fp16 --output results/t4_mlp_fp16.json
```

The remaining model-level milestone is checkpoint integration and generation
latency with the same inputs, precision and decoding configuration. Do not
infer model throughput from these standalone operator measurements.

The `benchmarks/bench_mlp_stages.py` follow-up times each stage in isolation
and repeats full-layer timing, but does not report kernel launches or a
compiled baseline. Its stage times may not sum to the full-layer latency.

### Stage timing follow-up

The measured stage JSON is
[`t4_mlp_stages_fp16.json`](../results/t4_mlp_stages_fp16.json), recorded on
the same T4 and software environment. Times are milliseconds.

| Tokens | Gate projection | Up projection | Down projection | SwiGLU eager | SwiGLU Triton | Full eager | Full Triton |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0.315616 | 0.315392 | 0.331776 | 0.006784 | 0.004448 | 0.958464 | 0.955200 |
| 128 | 0.401568 | 0.400672 | 0.464896 | 0.054624 | 0.035328 | 1.513472 | 1.490496 |
| 1024 | 2.934688 | 2.932896 | 4.700160 | 0.396896 | 0.237568 | 11.645792 | 11.556384 |

The projection timings are much larger than the activation timing. Isolated
stages and a complete layer have different cache and launch behavior, so the
numbers cannot be added to infer an exact share. The 1024-token full-layer
difference here is 0.089408 ms, versus 0.155040 ms in the earlier full-layer
run; a percent-level gain needs repetition and uncertainty estimates.

### Compiled PyTorch operator comparison

The original same-session measurements are in
[`t4_compiled_swiglu_fp16.json`](../results/t4_compiled_swiglu_fp16.json).
`torch.compile(swiglu_torch, backend="inductor", fullgraph=True)` is called
once before timing each shape, so compilation is excluded. All paths allocate
an output. Latencies are microseconds.

| Tokens × features | Eager | Hand-written Triton | Compiled PyTorch | Triton vs compiled |
| --- | ---: | ---: | ---: | ---: |
| 1 × 11008 | 6.848 | 4.448 | 4.448 | 1.000× |
| 128 × 11008 | 54.816 | 35.392 | 33.920 | 0.958× |
| 1024 × 11008 | 397.312 | 237.760 | 236.672 | 0.995× |

The final column is compiled latency divided by Triton latency; values below
one mean the compiled path was faster in this run. There is no observed
advantage over the compiled reference at these shapes. Repeated independent
runs would be needed to resolve the very small differences. Compared with
eager, the maximum absolute error was 0.00048828125 for the hand-written
kernel and 0.0078125 for compiled PyTorch. Both passed the comparison script's
`rtol=atol=0.01` check. The compiler may change FP16 intermediate rounding;
numerical accuracy must be considered alongside speed.

### Kernel trace

[`kernel_tables.txt`](../results/t4_profile_swiglu/kernel_tables.txt) and
four accompanying Chrome traces in the same directory were captured for
five iterations per provider and shape. Trace JSON contains 10 CUDA kernel
events for eager and five for Triton at both 1 and 1024 tokens: two launches
versus one launch per call. At 1024 × 11008, the table reports roughly
156.2 μs for SiLU and 228.2 μs for the subsequent multiply, versus 228.6 μs
for the fused Triton kernel, per call. At 1 × 11008, their kernel CUDA times
were approximately 2.7 μs plus 2.3 μs versus 2.3 μs. Profiler timings are
diagnostic and are not substituted for the `do_bench` latency numbers above.
